# 提示词包 · 引擎合并（tdm_synth + touch_tdm_synth → 单池 48 声部）

> **2026-10-24 更新：本文为历史评估，含已被 RTL 与仿真推翻的结论。后续采用 [提示词_引擎合并_V2.md](提示词_引擎合并_V2.md)。** V2 更正帧预算、满池替换、配置除法器、包络/ROM 精度和资源假设，推荐共享核心并保留 32＋16 固定分区。以下正文保留用于追溯，不作为当前执行依据。

**状态：未立项，本文档是可行性评估记录 + 若立项时的执行顺序。2026-10-24 写。**

**结论先说：不建议现在做。** 收益是净 700~1000 CLS，但

1. **只回收 2 个 DSP 单位**（26.5 → 24.5），而效果器包缺的是 DSP 和 CLS 两头，它只解一头；
2. **朴素合并在帧预算上溢出 103 个时钟**（1127 / 1024），会直接置 `overrun` 丢音；
3. 要收敛必须同时满足两个前提（见 §2.4、§3），其中一个是**触摸声部放弃 16 拍恢复除法器**；
4. 最大风险不是资源，是**声部抢占**，而现有 12 组回归**结构上抓不到**这个 bug。

额度请走零功能损失回收，见 `提示词_数字音频效果器.md` §4.3 第①条（`downloadable_song` 组合函数去重，约 350~450 CLS）。

## 0. 一句话目标（若立项）

把两台并行的 TDM 音源合成一台：`tdm_synth`（VOICES=32，服务红外 / 手势 / TEST32）与
`touch_tdm_synth`（16 声部，服务 16 个触摸 pad）合并成 **VOICES=48 的单池**，
触摸键成为第四个 producer，然后整个删掉 `touch_tdm_synth`。

## 1. 现状：两台引擎的实测对比

数据来自 `impl/gwsynthesis/PCM5102_UNIFIED_syn_rsc.xml`（2026-10-23 构建），CLS 按 1.92 logic/CLS 折算。

| | `tdm_synth` | `touch_tdm_synth` |
|---|---|---|
| 实例路径 | `u_gesture/u_audio/u_synth` | `u_touch_synth` |
| Logic | 3386（2498 LUT + 888 ALU） | 1957（1713 LUT + 244 ALU） |
| ≈CLS | 1760 | 1020 |
| Register | 2095 | 817 |
| BSRAM | 7 | 2（contexts 1 + touch_sine_rom 1） |
| DSP | 4×MULT27X36 = 8 单位 | 1×MULT27X36 = 2 单位 |
| 声部数 | 32 | 16（**硬件硬顶**，见 §5） |
| 触发方式 | **事件式**：FIFO 送 `{inc, timbre, frames, adsr}`，`remaining` 倒数到 0 自动释放 | **门控式**：`gates[15:0]` 按住就一直响 |
| context RAM | `reg [35:0] contexts[0:VOICES*16-1]`（`:43`），556 位有效 / 576 位填充，32×16×36 = 18432 bit = **正好 1 块 18Kb** | `reg [15:0] contexts[0:255]`（`:25`），16 声部 × 15 个字段 = 240 字，**4096 bit 占一整块 18Kb** |
| 包络算术 | **乘法插值**：`env_phase`(24 位累加) + `env_step` → `env_advance`，再 `× env_delta`（`:76-77`、`:513`），**零额外状态** | **16 拍恢复除法器**：`DIVIDE` 状态，`divide_left<=15`、`q_next`/`rem_next`（`:211-215`、`:132`） |
| 声部分配 | 先到先得，**无抢占**（`:155-157`） | `age` 计龄 + `oldest`/`victim` + `protected_limit`（`:36-38`、`:45`、`:219-221`、`:246`） |
| 每帧最坏占用 | 约 871 / 1024（见 §2.1） | **1024 / 1024，零余量**（见 §2.2） |
| 合计 | **5343 logic ≈ 2780 CLS，10 个 DSP 单位** | |

两台引擎**并行运行在同一个 1024 时钟帧里**，各自有独立的 1024 拍预算，互不挤占。
这是现状能跑通的原因，也是合并的最大障碍——合并后它们要**共用**一份 1024 拍。

## 2. 帧预算核算（决定性的一节）

> **本节所有拍数都是从 FSM 状态序列静态推导的，不是仿真实测。立项后第一件事是在仿真里放一个每帧时钟计数器把它们证实或推翻。**

### 2.1 `tdm_synth` 的真实拍数：每声部 16 拍、每事件 11 拍

**每声部 16 拍**（不是之前口口相传的 19）。状态从 `VOICE_ACCEPT=12` 走到 `VOICE_COMMIT=27`：

```
VOICE_ACCEPT(12) → LOOK_BASE(13) → LOOK_H2(14) → LOOK_H3(15) → LOOK_H4(16)
→ LOOK_AUX(17) → LOOK_AUX2(18) → PITCH_MUL(19) → PITCH_WAIT(20)
→ BODY_MUL(21) → BODY_WAIT(22) → BRIGHT_MUL(23) → BRIGHT_WAIT(24)
→ GAIN_MUL(25) → GAIN_WAIT(26) → VOICE_COMMIT(27)      = 16 拍
```

`VOICE_COMMIT` 回跳的是 `VOICE_ACCEPT`（`:554`），不回 `VOICE_PRIME`。
「19」是把 `VOICE_PRIME=11` 到 `VOICE_DRAIN=29` 的**状态编号跨度**当成了拍数——
`VOICE_PRIME` 每帧只进一次，**`VOICE_DRAIN=29` 在整个 case 里根本没被用到**（`:183` 声明后是死编号）。

**每事件 11 拍**：`EVENT_READY(1)` → `EVENT_PATCH(9)` → `EVENT_COMMIT(1)`，其中
`EVENT_PATCH` 从 `event_word<=7`（`:486`）数到 `15`（`:493-495`）= 9 拍。

**当前最坏帧（TEST32）**：32 个事件 + 32 个声部

```
32 × 11 = 352   （事件打包，event_quota 上限 32，见 :477）
32 × 16 = 512   （声部遍历，VOICE_COMMIT 无条件走完 slot 0..VOICES-1）
      + 7       （IDLE 1 + LFO1~4 4 + VOICE_PRIME 1 + PUBLISH 1）
    = 871 / 1024     余量 153 拍（15%）
```

### 2.2 `touch_tdm_synth` 的真实拍数：每声部 48 拍，带除法器 64 拍，**16 声部最坏正好 1024**

**这一条推翻了之前"touch 占约 210/1024"的说法——差了将近 5 倍。** 那个 210 是把「13 个 context 字段」误当成「13 拍」了。实际：

```
LOAD(1) + 13 × [READ_WAIT + READ_WORD](26) + ENV(1) + PITCH(1) + PITCH_WAIT(1)
+ WAVE(1) + WAVE_WAIT(1) + GAIN(1) + GAIN_WAIT(1) + STORE(13)      = 48 拍
+ DIVIDE(16)   ← 只在 ADSR 段切换那一帧发生（segment task 置 divide_left<=15）  = 64 拍最坏
```

模块头注释自己写明了这个设计意图：*"Worst-case 16 simultaneous segment divisions complete within the 1024-clock stereo frame"* → **16 × 64 = 1024，一拍不剩**。
`overrun` 判据在 `:146`：`if(sample_ce && state!=IDLE && state!=INIT) overrun<=1;`

> **✅ 这条静态推导已被实测证实**（`FX_PREFLIGHT_20261024.md:7-28`，测试 `./tools/run_sim.ps1 -Tests tb_fx_frame_budget`）：
> 同帧最大占用 **触摸合成 1012 / 1024**、七路弯音扫描 43、现有效果器 5；1411 个完整帧通过，超限帧 0、RTL `overrun` 0，
> 覆盖 4 个「同帧 16 声部包络除法」的边界帧（每次 256 个 DIVIDE 周期）。
> 1012 ≈ 我推的 16 × 64 = 1024，**误差 12 拍**。所以本节数字可以当真，不必再重新推导。
>
> **同时这份实测确立了一条对合并至关重要的事实**：触摸合成、弯音扫描、效果器**各用自己的 RAM 和乘法器**
> （`u_touch_synth.contexts` / `u_fsr_pitch_scaler.individual.u_bend` / `u_effects.memory`），
> **是并行硬件，不共享时分处理器**。三者忙碌周期的**并集只有 1012**，同时空闲只有 12 拍。
> → 「1012 + 43 + 5 = 1060 > 1024 所以塞不下」是**错的**（它们并行）；
> → 但「效果器自己有 1019 拍空闲」也**只在它自己的 FSM 内成立**，不能借给别的引擎。
> **合并的本质正是把触摸那 1012 拍的并行开销，压进 tdm_synth 的单一 1024 拍串行序列里** —— 这就是 §2.3 溢出的由来。

**含义：合并不能从触摸引擎那边"继承"任何时钟余量，它自己已经用满了。**

### 2.3 朴素合并 = 溢出 103 拍

48 声部单池，保持 tdm_synth 的 16 拍/声部，TEST32 仍要 32 个事件：

```
48 × 16 = 768
32 × 11 = 352
      + 7
    = 1127 / 1024     溢出 103 拍（10%）→ overrun，丢音
```

**这就是"朴素合并跑不通"的硬数字。** 注意溢出发生在**发送 TEST32 的那一帧**，也就是竞赛现场举证的那一刻。

### 2.4 唯一能收敛的配置

把 `event_quota` 上限从 32 降到 **16**（`:477` 的 `event_quota==32` 改成 `==16`）：

```
48 × 16 = 768
16 × 11 = 176
      + 7
    =  951 / 1024     余量 73 拍（7.1%）
```

**代价与可行性：TEST32 的 32 个音会分 2 帧触发，间隔 20.48 µs（总计 41 µs 铺开）。**
`sub_note` 本来就是每个 `EVENT_COMMIT` 递增一个（`:503`），跨帧续发是现成机制，不用改结构。
对秒级录音的频谱分析**完全没有影响**——41 µs 的启动离散度远小于 Audacity  Hann 窗在 16384 点下的频率分辨率。
**但这条必须在 `tools/check_test32_spectrum.py` 类的谱峰比对里显式确认 32 个峰仍然全部出现、幅度仍然一致。**

余量 73 拍（7%）比现状 tdm_synth 的 153 拍（15%）**紧一半**。任何后续给声部通路加状态的改动都会先撞这里。

### 2.5 想再要余量只有一条路，而它是功能损失

摘掉 `LOOK_AUX2`（`:525`）可把每声部从 16 拍降到 15 拍 → 48×15 + 176 + 7 = **903，余量 121 拍（11.8%）**。
但 `LOOK_AUX2` 捕获的是 `aux`，服务音色 6（金属/钟）和 7（弦乐）；要让它变成死状态必须先 `EXTENDED_TIMBRES=0`，
**那是砍音色，本包禁止**（理由见 `提示词_数字音频效果器.md` §1.4.2）。
另外注意：`LOOK_AUX → LOOK_AUX2 → PITCH_MUL` 的跳转是**硬编码在 case 里的，不受参数门控**，
光把 `EXTENDED_TIMBRES` 设 0 只会让 `aux`/`aux2` 寄存器被扫掉，**状态照走，一拍不省**。要省必须手动改跳转。

## 3. 合并的真正前提：触摸声部必须放弃恢复除法器

这是本次评估**最重要的新发现**，之前的分析里没有。

两台引擎算 ADSR 斜率的方式根本不同：

| | 怎么算斜率 | 每声部代价 |
|---|---|---|
| `tdm_synth` | `env_step` 是**配置期就除好的 24 位常数**，存在 `env_cfg[71:48]/[47:24]/[23:0]`（`:74`）。运行时只做 `env_phase += env_step` 累加，再 `env_advance × env_delta` 用**那颗已经存在的共享乘法器**（`:513`） | **0 拍** |
| `touch_tdm_synth` | 每次段切换现场算 `|target − gain| / duration`，用 16 拍恢复除法器（`:211-215`） | **16 拍** |

48 声部 × 16 拍 = 768 拍，光除法器就吃掉整个帧预算的 75%。**合并后绝对不能保留它。**

好消息是 `tdm_synth` 的方案**功能上更强**，不是妥协：
`env_delta = env_target − env_start`，而 `env_start` 是转换那一刻捕获的当前电平（`:77`），
所以「攻击到一半松手」这种任意起点它照样正确——恢复除法器能做的它都能做。

**需要补的一处**：触摸 ADSR 现在是 64 位裸时长 `config_snapshot[63:0]`（attack `[63:48]` / decay `[47:32]` / sustain `[31:16]` / release `[15:0]`，见 `:179`），
**没有预除好的 `env_step`**。合并后要在 `adsr_config`（`u_keymap/u_adsr_config`，现 464 logic）里加一个**共享除法器，只在 HC-05 写 ADSR 参数时跑一次**，
把触摸的三段时长也换成 24 位 `env_step`。这颗除法器不在音频帧通路上，所以不吃帧预算，
但它会让 `u_adsr_config` 长大——**这部分 LUT 增量要计入 §1 那张表的净收益，700~1000 CLS 的估算里目前没有它。**

**连带后果**：包络曲线从「逐拍精确除法」变成「24 位相位插值」，数值上会有细微差异。
`tb_touch_tdm_synth`、`tb_top_pedal`、`tb_touch_pedal_timing` 的期望值全部要重新推导，不是改个常数就完事。

## 4. 必须搬过去的四样（漏一样就是静默退化）

`tdm_synth` 是「击发 + 固定帧数衰减」，没有下面任何一样：

| # | 要搬什么 | 现在在哪 | 搬法 |
|---|---|---|---|
| 1 | **gate 保持语义**（最关键） | `touch_tdm_synth:175` `seen<=frame_gates[index]`、`:185-188` 松手才进 release | `tdm_synth` 现在是 `remaining` 倒数到 0 就释放（`:312`、`:328-329`）。要给 context 加一个 gate 位，按住时重载 `remaining`，或让 gate 直接控制释放 |
| 2 | **延音踏板** | `PEDAL_TAIL_MS=1200` → `TAIL_SAMPLES=(50000×1200+512)/1024 = 58593`（`:39`），4 段 `tail_duration()` 链式衰减（`:63-66`、`:198-202`）；`DAMPER_MS=10` → `DAMPER_SAMPLES=488` | `tdm_synth` 的 `remaining` 是 `[16:0]`（`:88`），上限 131071，**58593 装得下，位宽不用改**。但 4 段链式衰减（`tail_part` 0→3）要整段移植 |
| 3 | **normalizer 防爆音查表** | `:47-59`，16 路 case：2 声部→2048、3→1365、…、16→256，默认 4096；另有一条 `requested_pedal!=2 && requested_poly==16` 时强制 4096 的旁路 | 合并后 `voice_count` 上限从 16 变 48，**这张表要重算到 48 路**，而且旁路条件的语义要重新定义 |
| 4 | **运行时 `poly_limit`** | HC-05 `CMD_POLY_SET=57`（`hc05_keymap.v:148`）→ `poly_limit<=accumulator[4:0]`（`:650`），默认 16（`:329`），回读走 kind 25 的 `POLY,##` | 5 位装得下 48，但 `protected_limit` 与 `victim_valid` 的判据（`:45`、`:246`）要跟着改 |

## 5. 位宽与 BSRAM 连锁

| 项 | 现在 | 合并后 | 代价 |
|---|---|---|---|
| `slot` / `init_slot` / `read_slot` | `[4:0]`（`tdm_synth:48`） | `[5:0]` | 声部分配器全加宽 |
| `voice_active` | `[31:0]`（`:32`） | `[47:0]` | 输出端口加宽，`top.v` 与 `perf_live_state` 的接线要跟着改 |
| `rank_order` / `shift_rank` | `[0:VOICES-1]`，`:150-152` 的 32 位 AND 前缀链 | `[0:47]` | 前缀链从 32 变 48，**会回涨一点 LUT** |
| `allocation` 优先级循环 | `:156-157`，32 次降序覆盖 | 48 次 | 组合链变长，注意时序（当前 WNS 只有 +0.198 ns） |
| `contexts` | 32×16×36 = 18432 bit = **1 块 18Kb** | 48×16×36 = 27648 bit = **2 块** | BSRAM 47 → 48（还剩 8）。效果器包要吃约 4 块，两者叠加后余 4 块 |
| `touch_tdm_synth` 的 contexts | 1 块 | 删掉 | 回收 1 块 |
| `touch_sine_rom` | 1 块 | 若触摸声部改用 tdm_synth 的 `sine_table[0:255]`（`:198`）则回收 1 块 | **要确认两张表的数值是否逐点一致**，不一致就是音色变化 |

**净 BSRAM 变化约 −1 ~ +1**，不是瓶颈。

**触摸声部硬顶 16 的事实**：`poly_limit` 虽然能设到 31，但 `touch_tdm_synth` 的 `index` 是 `[3:0]`、
`contexts[0:255]` 只有 16 声部 × 16 字，**硬件上限就是 16**。合并进 48 池后触摸理论上能突破 16，
但物理上只有 16 个 pad，用不上。这条不用改，但别在 App 上把 `poly_limit` 的可选范围宣传成 48。

## 6. 和声与复音：合并前后的真实差异

**复音总数不变：48 → 48。** 现在是触摸池 16（独立）+ 传感器池 32（独立），两池互不相通；合并后是 48 共享一池。

**但和声能力有变化，必须先知道现状：和声只有一个来源——同时按住多个触摸 pad。** 另外两条和声路径都是死的：

- `sensor_poly_audio.v:96` 是 `.chord_valid(1'b0)`，**tdm_synth 的和弦入口硬接死 0**，`CHORD_FRAMES=17'd97656`（`tdm_synth.v:18`）是死参数；
- `song_sample` 那条 4 声部 `poly_synth` 在 `ENABLE_DEMO_SCORE=0` 下整个 generate 分支被裁掉，`top.v:480` 直接 `song_sample=16'sd0`。

**含义**：合并后如果 gate 保持语义（§4 第 1 条）没搬对，和声会**直接归零**，不是"稍微变差"。

## 7. 最大风险：声部抢占（现有回归结构上抓不到）

两台引擎的分配策略完全不同：

**`tdm_synth`（`:155-157`）—— 先到先得，无优先级、无回收：**
```verilog
allocation=rank_order[VOICES-1];
for (a=VOICES-1;a>=0;a=a-1) if(!voice_active[a]) allocation=a;
```
降序循环最后一次赋值生效 → 取**最低的空闲号**。满了就 `overrun<=1`（`:452`），**直接丢音**。
`rank_order` 那套 LRU 链（`:150-152`、`:499-502`）维护了新旧顺序，但**分配时根本没用它做回收**。

**`touch_tdm_synth` —— 有完整抢占机制：**
`age` 逐帧计龄（`:219`，物理按住的键 `age<=0` 不计龄）、`oldest`/`oldest_age` 挑最老的可回收声部（`:220-222`）、
`protected_limit = max(physical_work, frame_poly)`（`:45`）、
`victim_valid = oldest_valid && count_work - pending_work > protected_limit`（`:246`）、
被选中的 `victim` 走 10 ms `DAMPER_SAMPLES` 快速消音而不是硬切（`:181-182`）。

**后果**：不把抢占搬过去，**TEST32 一次触发 32 声部就把 48 池占掉 2/3**，剩下 16 个位置一旦也被红外/手势事件填满，
再弹触摸键就哑了。现在两池隔离，触摸永远有自己的 16 个 slot，**物理上不可能被传感器饿死**。

**为什么现有 12 组回归抓不到**：`tb_top_idle`、`tb_top_audio_record`、`tb_touch_tdm_synth` 等全部建立在两池隔离的前提上，
「TEST32 占满池子后弹触摸键」这个场景在现架构里**不可能发生**，所以没有任何用例覆盖它。
合并后它会变成一个**静默退化**——不报编译错、不报仿真 FATAL，只在现场"挥手之后琴键哑了"。

**必须新写的用例（在动任何 RTL 之前）**：
1. TEST32 触发后立即按住若干触摸 pad，断言 pad 仍然发声；
2. 48 池全满时新的红外/手势事件到达，断言被抢占的是**最老且非物理按住**的声部，物理按住的键不被回收；
3. 抢占发生时断言走的是 `DAMPER_SAMPLES` 消音而不是硬切（避免爆音）；
4. `poly_limit` 设成小于物理按住键数时，断言 `protected_limit` 优先保护物理键。

## 8. 执行顺序（顺序错了会白干）

```
0. 先在仿真里放每帧时钟计数器，证实或推翻 §2 的全部拍数推导。
   数字不对就停下重算，别往下走。
1. 写 §7 的 4 条抢占用例，先在【现架构】上跑——

3. 把触摸 ADSR 换成预除 env_step（§3），adsr_config 加共享除法器。
```

## 10. 禁止事项

- **禁止保留 `touch_tdm_synth` 的 16 拍恢复除法器**（§3）。48 声部 × 16 拍 = 768 拍，光除法就吃掉帧预算 75%。
- **禁止保持 `event_quota==32`**（§2.3）。朴素合并溢出 103 拍，溢出点正好是 TEST32 那一帧。
- **禁止先动 RTL 后补抢占用例**（§8 第 1 步）。顺序反了就没有任何机制能发现 §7 那个静默退化。
- **禁止用 `EXTENDED_TIMBRES=0` 换帧预算余量**（§2.5）。那是砍音色 6/7，功能损失。
- **禁止在本包里顺手做效果器或反之**。两件事都要动 `audio_effects` / `tdm_synth` 附近的资源，
   混在一起提交就分不清 CLS 差值是谁贡献的。效果器包见 `提示词_数字音频效果器.md`。
- **禁止用估算值交资源差**，每一项都要有快照实测报告，和同一天的基线比。
- **禁止把"仿真通过"表述为"实物验收通过"**。上板仍走 PCM5102 耳机孔对录 + Audacity。
- **禁止在 App 上把 `poly_limit` 宣传成 48**（§5：物理只有 16 个 pad）。
